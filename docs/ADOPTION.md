# 采用指南：把方法带到你的项目

这是供外部项目采用的模板与操作指南。根目录 AGENTS 和 PRD/DESIGN/TASKS 是 agent-matrix 自身的维护实例；不要把它们的需求、任务、已完成状态或扫描结论复制进你的项目。示例见 [EXAMPLE](EXAMPLE.md)，审核模板见 [Review 规范](reviews/README.md)。

## 接入步骤

1. 保存你已有工作，查看分支、暂存和未跟踪文件。先读目标项目适用的 AGENTS/CLAUDE/CONTRIBUTING 等规则；遇到冲突由负责人明确，不擅自替换。
2. 将下方“初始化 Prompt”交给你使用的 Agent。它必须先扫描，再增量补齐事实源；不要求安装 agent-matrix 或改变应用技术栈。
3. 若已有 wiki、spec、任务或审核目录，建立路径映射，保留一份有效事实源。不存在时默认使用根 AGENTS 与 docs 下三个事实源和 reviews。
4. 按后面的模板补齐缺失字段。未确认的业务问题写 TODO_CONFIRM，不按示例猜测。空仓库先确认范围，不编造运行时 API。
5. 审阅初始化报告。初始化到此停止；负责人之后选择一个任务或授权 Goal，才进入实现与测试。

整个过程不需要全新平台、MCP 服务或多个模型。一个 Agent 也能执行；同一 Agent 自检必须如实署名，不能包装成独立交叉审核。

## 初始化 Prompt（整段复制）

```text
你是当前项目的工程协作助手。目标是增量建立轻量闭环：
PRD → DESIGN → TASKS → CODE & TEST → REVIEW → DONE。
本轮只初始化治理文档，完成报告后停止，不执行开发任务。

先检查当前分支、git status、暂存/未暂存与未跟踪文件，再读适用的项目规则。
依次扫描 README、AGENTS/CLAUDE/CONTRIBUTING、现有需求/原型、设计/SPEC、
SQL/数据库、API、任务/TODO、CI，然后读真实代码和测试。
报告语言/框架、模块/真实目录、公共能力、数据与契约、实际构建测试入口。
规则：不修改业务代码、依赖、数据库、生产配置或部署；不提交/推送；
不覆盖删除已有工作。优先复用现有文档和路径，不建立第二套平行体系。
不要默认创建 agents/skills/workflows/memory/prompts/templates/mcp 等目录。

所有分析用 CONFIRMED / INFERRED / TODO_CONFIRM，附来源。
CONFIRMED 是有直接依据，不表示设计已批准；禁止猜测业务以填满文档。
没有代码时如实记录，不编造技术栈、测试结果、文件或方法。

默认事实源：AGENTS.md、docs/PRD.md、docs/DESIGN.md、docs/TASKS.md、docs/reviews/。
已有体系则记录等价路径并复用。需求、设计、任务、决策 ID 稳定且不重用。
PRD 必须包括背景/目标/用户、范围、功能需求、流程/规则、验收、非目标、待确认。
每项 REQ 有事实等级、来源和可判定验收；PRD 不写类名/SQL/实现路径。

先 PRD，再扫描相关代码，再 DESIGN，再 TASKS，禁止越层。
DESIGN：每项绑定 REQ、事实等级、DRAFT/REVIEW/APPROVED/BLOCKED、复杂度；
给出模块与调用关系、真实修改路径、新路径标 [NEW]、数据库影响（无则明确无）、
适用的接口/调用/共享数据契约、参数校验、错误/权限、测试方式。
SIMPLE 写位置/方式/验证；NORMAL 增加确定的接口、数据与文件契约；
COMPLEX 再补状态/并发/事务/幂等/一致性/性能/兼容/恢复与测试策略。
不要硬套 Controller/Service 分层。数据库、公共 DTO/接口、跨模块或重大方案
未经负责人确认不得 APPROVED。按复用→扩展→新增，不重复实现已有能力。
生成任务前检查：数据存储↔映射、入口↔输入输出、入口↔核心调用、核心调用↔存储、
设计↔已有实现、共享契约唯一性。按实际组件映射，不存在写 N/A 与理由；先消除冲突。

TASKS 是唯一进度源：维护状态统计、P0/P1、阻塞、进行中、下一可执行任务。
每项含 Task ID/名称、REQ、DESIGN、Priority P0～P3、Status、Depends On、
Owner/认领时间、Target Module/Files/API或Method、Implementation、Acceptance Criteria。
状态用 TODO/IN_PROGRESS/BLOCKED/REVIEW/DONE；目标文件真实或 [NEW]，未定 TBD。
核心逻辑先写或同步写边界/单元/集成测试，覆盖后才提审。
缺少确定设计不生成编码任务；可用范围确认/设计决策任务解除阻塞。

AGENTS 常驻规则：按 AGENTS→绑定REQ→绑定DESIGN→TASK→Target Files 按需读，
可先查任务索引定位 ID，不全量加载无关模块与历史。
负责人/协调者串行分配 Owner 后才写；同 Task/文件/共享进度仅一位写入者。
认领冲突都暂停，协调者决定；异常退出不超时夺权，核对成果后明确移交。
写 TASKS/reviews 前重读最新状态，局部更新或追加，不缓存覆盖。
十条铁律：不扩需求、不改无关、不无据重构、优先复用、不擅改契约、
不覆盖他人、不伪造测试、设计冲突停下记录、确认后及时回写、状态及时同步。
角色可建议 Codex 实现、Claude 安全/代码、Hermes 架构、Gemini 一致性，
但不强制模型、不虚构参与或独立审查。

同 Task 只维护一个 TASK-xxx-review.md。记录真实审核者、日期、范围、验证、结论。
问题含 Issue ID/Severity/Reviewer/Description/Evidence/Impact/Suggestion/Status/Verification。
OPEN→FIXED→VERIFIED；有反证可 REJECTED，P0/P1 驳回还需另一审核者或负责人认可。
后续审核先读历史并独立核实，再追加 Confirm/Rebut/新发现，不能删前序意见。
任何未解决 P0/P1 强制 FAIL、禁止 DONE/合并；FIXED 不算清零。
结论 PASS/PASS_WITH_CONDITIONS/FAIL；有未满足验收的条件不能 DONE。
审核者先登记结论，Owner/负责人核对 PRD+DESIGN+Task验收+真实必要测试+
审核完成+P0/P1清零后登记 DONE，记录登记者、日期、审核链接。
争议按观点/代码/实际测试/契约裁决，仍不明则 TODO_CONFIRM 交负责人。

演进：需求变化先 PRD→DESIGN影响/更新→TASKS影响/更新→CODE；
设计不可行先记录原因/最小修正/影响，再更新设计任务、重新确认后继续。
待确认事项确认后立即回写需求/设计/任务/统计，移出待确认列表并保留决策依据。
历史 DONE 不删除，增量变更新建任务。Goal 默认按 P0→P1→P2→P3 每次串行一个
依赖已满足的任务，遵从负责人另行限定；本轮初始化不得自动执行。

最后检查 PRD↔DESIGN↔TASKS↔真实代码，输出八部分报告：
项目现状、需求统计/差异、设计统计/契约/风险、任务看板/依赖/下一任务、
一致性检查、文件变更、真正待负责人决定的问题、下一步建议。
明确未运行验证及原因，输出后停止，等待负责人选择 Task 或新 Goal。
```

## 项目 AGENTS 最小模板

只把目标项目已经确认的事实填进占位符。以下是模板，不能直接声称已完成扫描或测试。

```markdown
# Agent 规则
- 项目：<目标、真实技术栈/目录、构建测试命令；未知写 TODO_CONFIRM>
- 事实源：<现有 PRD / DESIGN / TASKS / reviews 的唯一路径映射>
- 加载：本规则 → 绑定 REQ → 绑定 DESIGN → TASK → 目标代码；只读相关章节。
- 认领：协调者串行登记 Owner、时间、文件；冲突先停，移交先核对成果。
- 写入：同 Task/文件单写；进度和审核写前重读，精准更新/追加，不覆盖历史。
- 十条铁律：不扩需求、不改无关、不无据重构、优先复用、不擅改契约、
  不覆盖他人、不伪造验证、设计冲突停下记录、确认及时回写、状态即时同步。
- 执行：先查依赖/设计/Git，IN_PROGRESS → 测试与实现 → REVIEW → 满足门槛 DONE。
- 变更：需求 → 设计 → 任务 → 代码；设计不可行先记录/更新/重新确认。
- 审核：单任务单主报告，多轮追加；问题字段和门禁见项目采用的 review 规范。
- 熔断：P0/P1 未 VERIFIED 或未有效 REJECTED 强制 FAIL；驳回须反证及认可。
- DONE：审核结论先登记，Owner/负责人核对验收与真实验证后登记日期/审核链接。
- 初始化：仅扫描/文档，不开发/迁移/部署/装依赖/自动提交，报告后停止。
- 后续授权：指定 Task 或新 Goal 后按授权执行，不把初始化停止条件永久化。
- 角色：按能力分工，模型只是建议，单人自检如实署名。
```

## PRD 最小契约模板

```markdown
# 需求事实源
## 背景与目标
<目标/来源，区分 CONFIRMED、INFERRED、TODO_CONFIRM>
## 用户角色与范围
<用户、必做、不做>
## 需求
### REQ-001 <需求名称>
- 事实等级：CONFIRMED / INFERRED / TODO_CONFIRM（选一项）
- 来源：<用户确认/文档/代码证据，日期>
- 需求：<只描述业务要什么>
- 验收：<可判定的输入、场景、结果与边界>
## 流程与业务规则
<含异常场景，不写实现细节>
## Out of Scope
<明确不做的范围>
## 待确认与决策关联
<Q-ID、影响的 REQ、负责人问题、确认后回写动作；确认后链接 DEC-ID>
```

## DESIGN 最小契约模板

```markdown
# 设计事实源
## DESIGN-001 <设计名称>
- PRD：REQ-001
- 事实等级：<CONFIRMED / INFERRED / TODO_CONFIRM>
- Status：<DRAFT / REVIEW / APPROVED / BLOCKED>
- Complexity：<SIMPLE / NORMAL / COMPLEX>
- 证据：<先扫描的真实文件与已有公共能力>
- 模块/调用：<复用→扩展→新增，按实际结构>
- 文件：<真实修改路径；新增标 [NEW]；未定 TBD>
- 数据库：<无，或表/字段/类型/默认/NULL/键/索引/关系/兼容/迁移草案；不执行>
- API/调用：<Method/URL/入口方法或其他协议、输入输出、权限、校验、错误>
- 核心方法：<签名、参数、返回、异常、事务；不适用写原因>
- 共享数据：<唯一归属、字段/类型/必填/校验/含义>
- 技术规则：<按复杂度补充状态、幂等、并发、缓存、重试、一致性等>
- 验证与恢复：<边界测试、命令、风险、必要的回退方案>
- 一致性检查：<存储↔映射、入口↔数据/调用、调用↔存储、现有能力、共享契约>
- 批准：<需要时记录负责人/日期/依据，缺少批准不能自写 APPROVED>
## 决策记录
<DEC-001、Q/REQ、决定者/日期、决定/依据/影响；被替代的记录保留>
```

## TASKS 最小契约模板

```markdown
# 唯一任务进度
## 全局看板
| Total | TODO | IN_PROGRESS | BLOCKED | REVIEW | DONE |
| --- | --- | --- | --- | --- | --- |
| 1 | 1 | 0 | 0 | 0 | 0 |
焦点：P0/P1、阻塞、进行中、下一可执行任务（依赖已满足）。
## TASK-001 <名称>
- PRD：REQ-001
- DESIGN：DESIGN-001
- Priority：P1
- Status：TODO
- Depends On：无
- Owner：未分配
- Claimed At：未认领
- Target Module：<真实模块>
- Target Files：<真实路径，或 [NEW] 建议路径；未确定 TBD>
- Target API / Method：<设计中已定义的准确签名或不适用原因>
- Implementation：<先写/同步写边界测试，再按确定契约实现，运行验证，进入审核>
- Acceptance Criteria：<满足需求/设计、编译与适用测试真实通过、审核无未解决P0/P1>
- Review：<审核完成后登记唯一主报告路径>
- Completed By：<验收满足后登记，不提前填>
- Completed At：<验收满足后登记日期，不提前填>
```

审核模板采用 [reviews/README.md](reviews/README.md)；在目标项目中建立等价主报告路径，不另建按模型分类的副本。

本仓库检查器针对 agent-matrix 的实例结构，不是任意项目的通用规范解析器。外部项目可采用字段和流程，但若复用检查器，必须先适配实际路径、编号、统计格式与发布资产清单；不得强行改造业务目录来满足本仓库脚本。

## 技术栈与设计深度适配

| 场景 | 接入方式 |
| --- | --- |
| Java / Spring | 扫描真实 Maven/Gradle、多模块、入口/服务/存储与测试；不凭模板新建 ServiceImpl |
| Python | 扫描实际框架/包、数据访问、环境与测试命令；CLI/库可没有 HTTP 层 |
| Node.js / 全栈 | 扫描实际工作区、路由/前后端契约、包管理器与测试；不默认 Express 或某个目录 |
| 文档/脚本/空仓库 | 没有运行时层标 N/A；纯文档做链接/一致性检查；业务范围未确认时只建决策任务 |

这是适配方法，不是“已在所有框架生产验证”的声明。采用项目应补充自己实际的验证命令与证据。

SIMPLE 只需位置、方式、验证；NORMAL 增加模块/文件、接口、数据和边界；COMPLEX 再增加调用链、并发/一致性、性能、兼容与恢复。按需裁剪不等于省略实际风险。

## 后续指令

- 指定任务：“执行 TASK-xxx，遵守项目 AGENTS，先检查依赖、设计和 Git，完成验证与审核后回写。”
- Goal：“在此范围内按优先级串行推进依赖已满足的任务；缺少决定性输入时记录阻塞，不扩展范围。”
- 需求变更：“先更新 REQ，再分析设计和任务影响；历史 DONE 保留，新建增量任务。”
- 设计不可行：“暂停相关实现，记录原因、最小修订与影响；更新设计/任务，经必要确认后恢复。”

模板只能约束流程，不能自动建立跨进程互斥、模型服从或生产质量保证；具体采用方式和权限由项目负责人决定。
